# Performance measurement

The suite measures production paths at three levels: kernels/protocol, controlled stream APIs, and real transports. Core cases support an optimization loop; extended cases cover boundaries, ownership, runtime placement and flow control. Neither tier is a production workload distribution. Diagnostic examples and allocation counters are separate from ordinary wall-time measurements.

## Run

```sh
# Registration, then all enabled correctness smoke cases; no performance samples.
cargo bench --locked -- --list
cargo bench --locked -- --test
# Curated default-feature core; choose a target to narrow it further.
cargo bench --locked -- '/core/'
cargo bench --locked --bench stream_tokio -- '/extended/'
# Production feature bundle, including both runtimes and optional transports.
cargo bench --locked --features full -- --test
# Independent runtimes without compression, and the minimal feature set.
cargo bench --locked --no-default-features --features tokio-runtime,http2,http3 -- --test
cargo bench --locked --no-default-features --features compio-runtime,http2,http3 -- --test
cargo bench --locked --no-default-features -- --test
```

Run the relevant commands when changing benchmarks. Replace `--test` with `--list` to inspect active cases for a feature set, and check that the expected suites appear and IDs remain unique across targets. Linux full/all-features includes io_uring cases. Running on macOS does not validate Linux or another instruction set. Required runtime/kernel capabilities must be present; failures are not silently skipped.

Every target accepts normal Criterion filter, list, test and baseline options. The library and application binaries have `bench = false`, so their libtest harnesses do not intercept Criterion arguments. Custom CSV programs are examples, not implicit cargo bench targets.

```sh
cargo run --locked --release --example receive_state_diagnostic -- --test
cargo run --locked --release --example delivery_diagnostic -- --test
cargo run --locked --release --example bench_memory
# TLS representative cases use the rustls backend.
cargo bench --locked --features rustls-webpki-roots --bench transport -- '/rustls/'
```

Memory instrumentation installs a counting System allocator and cannot coexist with the library's `mimalloc` allocator. Run `bench_memory` without `mimalloc`; it rejects that feature, including when enabled by all-features. The diagnostic is not an allocator comparison and reports no timings.

## Hot paths and ownership

| Target | Production paths and cases | Feature requirements |
| --- | --- | --- |
| `kernels` | mask/copy-mask and real mask RNG, 64-byte base with selected 16/32/64-byte alignment classes, SIMD tails and 2047/2048/2049, UTF-8 with std reference, prepared/copy-inclusive frame parse, encode | None; the build selects the available implementation |
| `protocol` | message containers, raw/typed validation, fragmentation, incremental input, fresh/reused state, encode/decode roundtrip, cork slices/consume | Plain cases always; compressed limit cases require `permessage-deflate` |
| `deflate` | reset/takeover encode and decode, threshold 31/32/33, repeated/seeded sequence, configuration, changing message sizes, shared/dedicated concurrency | `permessage-deflate` |
| `stream_tokio` | real unified/native split receive and send over controlled I/O, first/burst delivery, retain/drop, partial/Pending, server 8191/8192/8193, vectored/scalar and feed/flush | `tokio-runtime`; compressed cases separately gated |
| `stream_compio` | real ownership-based unified/native split receive and send, including background writer and actual compression | `compio-runtime`; compressed cases separately gated |
| `transport` | existing duplex/TCP placement/backpressure experiments; real Tokio/Compio TCP/H2/H3 round trips; default/restricted H2/H3 windows; rustls handshake/steady state; Linux io_uring bridge | Each runtime and transport gates only its own cases |
| `lifecycle` | HTTP request/response parse/build, extension/subprotocol fields, keys, stream construction/split, complete in-memory HTTP upgrade | Syntax always; each runtime gates its own construction/split cases; HTTP upgrade requires Tokio |
| `pubsub` | publish and drain, empty topic, sender exclusion, finite churn, continuous tracked churn | `tokio-runtime` |

`support/` contains measurement implementations and shared fixtures. An implementation can be referenced by several targets, but a measurement is registered by only one owner. Logical ID prefixes remain independent of support filenames. Directory components must stay short and distinct after Criterion's filename sanitization; Criterion 0.8.2 truncates each component to 64 bytes and has no executable namespace. Review IDs across executables when adding or renaming cases.

## Measurement contracts

- An iteration has an explicit message/byte count. Throughput metadata does not convert batch time into individual-message latency or percentiles. Empty work uses an operation denominator.
- Prepared parsing excludes wire allocation/copy and returned-frame destruction; copy-inclusive parsing includes its documented allocation/destruction. Fresh protocol state and reused state remain distinct. See [codec contracts](CODECS.md).
- Controlled receive repeats a finite source burst. A read never crosses into the next burst, although destination capacity and the configured read limit can split it. Control cases contain one Ping and fifteen data messages per burst; they measure API delivery and control forwarding, not confirmed peer receipt of the automatic Pong. Payloads carry a sequence prefix or JSON sequence field; complete cycles are validated before and after sampling. `window_fit` covers plain Tokio reception with exact wire lengths 24576/32767/32768/40960, and a separate 40960-byte retained-payload case. A captured connection verifies the initial read length against the actual stream API. The initial full read is on the corresponding side of the 32768-byte reclaim hint; later reads depend on parser consumption and ownership. These cases do not assert a particular memmove size. Compio has no equivalent Tokio reclaim-hint branch; its plain-unified `reserve_spare_fresh` cases use a 65531-byte payload (65535-byte wire) and leave 4095/4096/4097 bytes after the first partial-frame read. A captured fresh connection verifies exactly two reads, their full byte count and final destination capacity: only below 4096 bytes does the destination grow, according to Compio's 8192-byte reserve request. On the other side the complete frame fits without any later reserve. Each measured iteration constructs a fresh connection outside timing and times one full receive/drop, including the clock bracket; a warmed buffer would not retain the specified spare capacity. Split uses the same reserve helper and is not duplicated here. `read1`, one header cut, one body cut and self-woken Pending are independent cases; body cuts use the actual wire length, including compressed output.
- Receive `burst` includes next(), message destruction and the selected retention queue policy. `first` accumulates only the first next() duration of each burst; the remainder is drained outside each measured interval. It includes clock overhead and is a steady-state first-delivery experiment, not a network arrival percentile. `first` is registered only for the core JSON burst and the 128-message burst. Timed bodies use concrete unified/split types. Runtime destruction releases remaining tasks after each sample.
- Controlled writes measure local completion, message cloning and normal encoding/compression. A separate captured connection validates bytes, role, RSV1, output order and partial/Pending behavior. Every message in both cold and warm captured cycles must short-write when requested: the oracle compares individual requested and accepted lengths and requires 2–4 successful write calls per message. Partial cases use eight independent seeded 8192-byte Binary messages and a fixed 4093-byte limit for both plain and compressed paths. Other compressed writes at 256 bytes or above rotate structured JSON messages spanning at least 64 KiB. The 32-byte small-message controls use the same seeded Binary sequence across kinds, with an eight-byte sequence number and seeded pseudorandom remaining bytes; the cycle spans at least 64 KiB so it is not a short dictionary-resident repeat. These small send payloads have little compression opportunity, whereas small Binary receive payloads use compressible `0x42` padding plus an eight-byte ASCII sequence number and are independently encoded per frame. The send and receive cases track their respective workloads; their timing difference does not isolate encoding versus decoding cost. The 31/33-byte controls use the same construction; compressed unified threshold cases at 31/33 bytes verify RSV1 clear/set respectively. Capture locks are absent from the timed sink; the inactive trace-option check remains. The sink accepts/discards bytes and does not model kernel throughput. Unified server segmented cases verify vectored dispatch, and plain `batch16` feed verifies the 16-IoSlice limit. Batch cases use feed/flush only; compressed feed measures its real buffering path without claiming segmented output. Native split is measured according to its real API, without inventing feed batching for it. Both split writer APIs require mutable access and expose no clone; these cases use one application sender. Ping receive cases exercise the separate control driver, while existing duplex backpressure cases cover a slow peer.
- Compression wrapper-only cases include `rsv1_clear` in their names; compressed stream cases must actually compress except for explicitly named below-threshold controls. Ordinary controlled receive cases use independently compressed frames. `takeover_json` primes one continuous encoded period P1, then replays P2 at the same phase; decoded periods span at least the 32 KiB dictionary. Several cycles must roundtrip, and at least one encoded message must fail to reproduce its payload with a fresh decoder, proving cross-message history is exercised. The JSON corpus repeats record keys with independently changing numeric/boolean values and fills the final unused record slot with a changing lowercase `note` string; no trailing whitespace is added. The note occupies about 20.4% of the 256-byte corpus and 1.0% of the 4096-byte corpus, so its content materially affects the small-message compression result; the corpus does not duplicate adjacent payloads; it is a synthetic model, not a measured production distribution. Encoding context cases measure valid evolving sequences; a repeated seeded corpus may become compressible with takeover, so it is not described as permanently incompressible. Context validation consumes matching encoder/decoder sequences before timing.
- Shared and dedicated compression use matching no-takeover semantics. Worker initialization and validation finish before the timed barrier release; joins are timed. Worker counts exceeding available cores are oversubscription experiments. The private pool has four slots per role window.
- Socket round trips include send, full peer echo and receive; setup/handshake and two full-payload checks are outside timing. They report round-trip work, not one-way latency. Both ends use sockudo, TCP_NODELAY where available, and disabled automatic heartbeat/idle timeout. Socket H2/H3 cases use the production handshake/adapters; adapter-only cases separately measure the standalone H2 wrapper over duplex and H3 DATA/raw-QUIC wrappers (including drivers, without WebSocket framing). The H3 DATA component reuses the test connection fixture; it is not a handshake measurement. Restricted windows are explicitly named. H2 restricts both directions; H3 restricts the client receive window while the supplied server endpoint keeps its transport defaults. Rustls full handshake disables client resumption and is measured separately on an in-memory duplex. Original batch/drain/local-completion cases retain their own contracts in [stream contracts](STREAMS.md).
- PubSub queues are drained every iteration. Continuous churn reports minimum completed churn cycles observed during a measured batch; zero means that sample did not exercise concurrent subscription work. It does not prove every publication contended on a lock. Finite churn remains a different combined-completion experiment. New selection cases include a verification-mode branch, but full payload assertions run outside timed iterations.
- Prototype protocol/write models remain explicitly named controls; they do not count as production API coverage. No subtraction of raw/model time establishes exact codec cost.

Small-message core stream cases enable inactivity tracking with 3600-second ping/idle intervals; the small server receive and send cases have matching `timers_off` controls in extended. This measures enabled, not-yet-due timer work, not production-default deadline expiry. Continuous inbound traffic postpones inactivity deadlines; send-only fixtures have no responding peer and must finish before their configured deadlines. The core plain-unified `large_timers_off` receive cases and Tokio `segment_timers_off` send retain timers-off to isolate their buffer/write paths. Default timers, idle-only/ping-only attribution and real peer behavior remain in the transport experiments.

Controlled-stream immutable fixtures and independent capture proofs are cached lazily once per selected ID, outside sample state. Laziness preserves Criterion filtering: listing or selecting another case does not run unrelated I/O probes. Deflate JSON encode/decode cases likewise share lazy immutable corpus preparation and its independent cyclic proof; their dictionary priming and post-sample phase checks remain per sample. Every controlled-stream sample still constructs a fresh runtime. Ordinary stream cases create a fresh connection per sample; steady-state receive warm-up and post-sample state checks remain per sample. Reserve-spare cases instead use a fresh connection per iteration and deliberately do not warm its read buffer. The `configuration` compression group compares complete default/low-memory presets (window, takeover, level and threshold), using the same structured message sequence; it does not isolate a single setting.

Lifecycle `construct_drop` enters the runtime and prepares Config plus an allocation-free controlled transport outside timing. Construction and destruction of the WebSocket object are timed; no duplex allocation is included. `split` separately times split construction and cleans up outside its timer.

`bench_memory` reports allocation/reallocation calls, cumulative requested allocation bytes, peak additional live bytes and retained additional live bytes. The denominator is the reported message count. Construction is included, input fixture creation is excluded, and returned state remains alive for the retained snapshot. These are allocator-requested bytes, not allocator usable size or RSS. Measurements use one thread and a 32/65536/32 binary sequence, including actual Tokio receive-window turnover with immediate drop or 16 retained payloads followed by release and a small-message recovery phase. Encoder and decoder reset/takeover counters instead use 256/65536/256-byte JSON messages. Shared runtime/fixture/codec initialization is warmed outside the counters; each measured stream/codec is still newly constructed. Encoder and decoder counters are separate; the ordinary benchmarks do not install these counters.

## Compare revisions

```sh
cargo bench --locked --bench kernels -- 'core/mask_reference' --save-baseline before
# Build the candidate with the same benchmark sources and configuration.
cargo bench --locked --bench kernels -- 'core/mask_reference' --baseline before
```

Keep the harness revision constant when comparing production changes. A harness migration, changed fixture or new timing boundary requires a new baseline; old output is retained but is not evidence of a library speedup. Record source and harness revisions, executable hash, rustc/target, profile, features, RUSTFLAGS, allocator, runtime placement, CPU/OS and exact commands. Use independent Criterion output directories for independent campaigns; do not change target directories to bypass an active Cargo lock.

The repository defaults to `-C target-cpu=native`. `RUSTFLAGS=""` selects the toolchain's default target assumptions and matches CI; keep these result populations separate. The bench profile uses thin LTO while release uses fat LTO. Default features and `full` exclude `test-util`; all-features enables it and switches the Tokio connection clock from quanta to Tokio. See [connection clock](../README.md#connection-clock). RNG feature priority is getrandom, then rand_rng, then fastrand, so all-features also changes the client mask generator. All-features is useful for correctness coverage, not the default-production-clock performance baseline. Steady-state Tokio suites explicitly call `init_clock()` before runtime work; they do not measure cold-process calibration.

The dependency migration to Criterion 0.8 and rand 0.10 requires fresh baselines: pin the lockfile as well as harness sources, and revalidate seeded corpus bytes and compression properties rather than assuming a fixed seed preserves them across RNG versions. Do not compare measurements across this dependency change as if only production code changed.

Establish noise with independent A/A processes before interleaved A/B comparisons. Report effect, intervals and matching controls; samples within one process are not independent trials. Choose warm-up, measurement time and samples from observed repeatability and the effect to detect. The full extended matrix is intentionally not the daily loop. Benchmark registration and smoke are manual checks. Existing CI `clippy --all-targets` checks enabled benchmark code but does not execute its fixture assertions; there is no CI wall-time regression threshold.

For tail latency, retain scheduled arrival, actual send and complete receive timestamps, distinguish paced/saturated traffic, and report sample support. [Delivery diagnostic](DELIVERY.md) documents the existing tungstenite peer and trace overhead. Its short smoke does not qualify P99. Assembly/instruction counts can investigate code generation; timing ratios alone do not prove scalar/vector execution. Gungraun is not required by this suite; add a pinned backend only for an identified instruction-count question.
